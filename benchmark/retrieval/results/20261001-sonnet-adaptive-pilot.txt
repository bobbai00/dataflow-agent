Sonnet 5.5 adaptive retrieval pilot — 2026-10-01
================================================

Conclusion
----------
The current prompt already gives the requested guidance. Sonnet's retrieval
choices were generally sensible in this small pilot: sample_stats for large
intermediate results, sample for raw format checks, and full for small result
sets or filename lookup. It did not retrieve a large parsed table in full.
Rationales did not always explicitly justify full. Statistics were usually
requested alongside the final calculation rather than before constructing it.

This is four complete original KramaBench questions, one attempt each, not
the full 104-task benchmark. All four passed the original evaluator (score
1.0). No production code or prompt changed, no task retried, and no result
was overwritten. This pilot tests view selection with flow evidence on;
it does not establish an accuracy improvement from the guidance.

What the agent was told
-----------------------
The actual saved prompts contain:
- "For a large parsed table, start with `sample_stats` when checking data
  quality or distributions. Project to relevant columns if a wide table
  hides the needed statistics."
- Full is "For small final results or decisions requiring individual records;
  a capped view remains partial."
- "For large tables, project, filter or aggregate before requesting `full`.
  Explain why individual records are needed."
- Samples are retained records, not random samples. Compute searches,
  comparisons and aggregates over full data in the graph.

A concise statement of that policy is: Use sample_stats to understand a
parsed result and check data quality. Use sample for layout checks. Use full
when you need individual rows, ordering or relationships between columns;
reduce large tables first. Small final tables can be read directly in full.
There is no need to retrieve the same small answer twice merely to follow
an unconditional stats-first rule.

Actual view choices
-------------------
15 successful reads: full 8, sample 4, sample_stats 3. Two further
sample_stats requests failed because execution had not produced a result;
these are included in the 17 attempted retrieves, not the success counts.

- Sample_stats: 55 first-per-state rows, 303 monthly records, 30,765 mapped
  beach records. Five records each; all three include column statistics.
- Sample: raw file/header previews. These have no parsed-column statistics.
- Full: a 15-line preview; six output states; one beach count; five ranked
  windows; six New England state names; two versions of a 15-row metro
  ranking; 52 filename groups. All were complete, each 248–2,316 characters
  including flow evidence. Six were below 2,000 characters. The two larger
  outputs include Cast and Join diagnostics; no bulk parsed table was read.

The filename lookup could be narrowed to relevant states, but its full
52-row table is only 1,076 characters. The one-row count and five-row ranking would also have been complete as
samples. Full is reasonable for these small final tables; the prompt allows
reading them directly without a preliminary statistics call.
There were no repeated successful reads of the same operator/version/view.

Concrete flow-evidence use
--------------------------
In legal-hard-14, the first ranked output showed failed conversions of
"2,571", "2,613", "1,414", plus other failures: 8/35 rows. The upstream
Join also reported only four of six requested states matched, explicitly
naming New Hampshire and Rhode Island as unmatched. Subsequent calls checked
filename-derived state names and normalized both names and numeric text.
The new ranking matched all six states and returned the correct top five
names/counts. Its remaining 24/48 Cast failures were source footer/blank
rows, independently confirmed. The stale comma-failure examples were absent
from the new producing version. Sonnet deduplicated overlapping metros in
its final response rather than adding a graph operator.

In environment-easy-3, full of the one-row count also carried the intermediate
Join's 1,138 matches and 33/38 unmatched beach keys. The final answer described
these exclusions correctly. It selected community-plus-name identity before
receiving those diagnostics, so this supports verification, not a claim that
metadata caused that key choice.
