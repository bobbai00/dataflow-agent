Claude action-interface validation — 2026-10-01

Conclusion

Sonnet 5.5 used substantially fewer calls than Haiku 4.5 on these two diagnostic
KramaBench tasks. It still sometimes answered outside the Dataflow tool. The
first pilot exposed a correct plain-text answer that failed the required Answer
contract. After a concrete repair example, the follow-up passed both tasks for
both models. Haiku still made graph and expression mistakes and repeated
exploration. Neither pilot showed an engine-result or prefix-cache invariant
failure. These selected cases do not establish full-benchmark accuracy or cost.

Protocol

Original KramaBench tasks: environment-easy-2 and wildfire-easy-15. Each model
ran once per task at each revision. Both tasks and both models were repeated
after the Answer fix; all initial attempts and their official scores remain
recorded. These are complete single-question tasks, not component subtasks.

Native mode, DELTA context, sample_stats only, flow evidence off, 2,000-character
samples with at most five rows, a separate 2,000-character statistics budget,
100,000-character retained full results, and 25 completed model calls maximum.
Thought replay and code snapshots were off. This tests a fixed retrieval view;
it does not test adaptive choice among views or automatic flow evidence.

The provider aliases were claude-haiku-4.5 and claude-sonnet-5.5; the latter
resolved to anthropic/claude-sonnet-5-5. Sonnet used provider-default thinking
and effort with automatic tool choice because it rejects forced tool use.
Strict typed inputs remained enabled; the final Answer contract was enforced
locally. Sampling parameters unsupported by Sonnet were dropped.

Scores below come from the original KramaBench task evaluator. Pass means a
score of 1.0. Model-call counts exclude feedback-only and synthetic final-error
events. Costs cover agent model usage, including cache reads/writes; they omit
benchmark scoring, infrastructure and standalone gateway probes.

previous call's cached prefix (previous read plus write). Usage totals match

Follow-up manual audit: why Haiku used more calls

The environment trace used three calls for the initial Edit, Execute and
Retrieve, although those actions had known arguments and could be batched.
It then confused the raw-line preview schema with the parsed full-scan schema,
adding a redundant CSV parser that expected file/line columns. Four failing
build/execute attempts involved the mixed-file union types, a cast of decimal
Indicator Level values to integers, that redundant parser and unsupported
conditional aggregate syntax. Indicator Level was not needed for this answer.

By trace step 21 (model call 21), above_avg already contained all eight answer
years. Its statistics said full=8 rows, enumerated all eight Year values and
reported other=0. Haiku explicitly recognized the full list, then spent four
more model calls creating, running and reshaping another verification table.
The final filter/project edits were not executed before Answer. The Answer was
supported by the earlier retrieved result. Remaining-budget feedback occupies
trace steps 23 and 26 but is not counted as a model call.

In wildfire, calls 3-10 were description discovery and repairs. A repeated
Retrieve and identity/renaming Process wrappers kept returning five sampled
rows. The sample_stats-only arm did not offer full retrieval. Filtering the
original description table to size/wind rows ultimately returned the three
needed rows. Two missing-edge executions and one wrong-column execution each
also produced a failure on the following Retrieve, yielding six failure
observations from three failed execution attempts. Across the pair, ten failure
observations therefore represent seven failing build/execute attempts, not ten
independent faults.

A semantic issue escaped the official Yes/No score. Haiku filtered July with
182 <= start_day_of_year <= 212 for every year. Independent source replay found
2,003 selected rows versus 2,000 calendar-July rows: 15 June 30 inclusions and
12 July 31 exclusions in leap years. Its Pearson result -0.010354101410384979
matches that incorrect selection; calendar July gives -0.011635324876752735.
Both support No, so the official pass remains unchanged. Sonnet used the month
from start_date. The benchmark reference script itself uses a fixed day range
(181 <= day < 213), so it cannot validate calendar-boundary correctness.
Engine/profile invariant checks do not prove the model's transformation is
semantically correct. This issue has been identified, not fixed by the two
interface commits; the original evaluator and task scores were left intact.
